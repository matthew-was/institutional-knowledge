check `docker exec ik-ollama nvidia-smi -L` and that `ollama ps` shows a GPU share. A real
deployment needs that as a health check plus a restart policy.

## Key findings (full evidence in the results document)

- Digital PDFs: use the PDF's own text. It beat every OCR option.
- Scans: Tesseract (the current default) is clearly beaten by vision-language models run
  through Ollama with a strict prompt, thinking off and temperature 0.
- Of the vision models, the Qwen family led. Gemma, GLM-OCR, DeepSeek-OCR, Qwen3-VL and
  Granite-Docling did not beat it (Granite-Docling cannot be driven through Docling here
  because Ollama strips its structure tokens).
- A **second reader** (a different model reading the same page) flags the primary
  reader's real errors far better than Tesseract does, at a modest number of flags per
  page. Matching is exact on words, and the ground truth is never used to decide a flag.
  Re-run with `python -m ocr_bakeoff.crosscheck` (tested module).
- Resolution: 200 dpi equivalent versus 300 moved one model's score about a point; not a
  deciding factor.
- Earlier claims that were wrong and were corrected in the results document: that a
  Tesseract cross-check catches every handwriting error, and a key-fact count that
  included excluded items.

## Recommended design (awaiting the owner's decision)

- **Primary reader `qwen3.6:27b`**, strict prompt, thinking off, temperature 0, for the
  quality of the reading. It does not fit the cards fully (runs about 24–30% on CPU).
- **Second reader `qwen3.5:9b`**, which also serves interactive queries, giving a
  per-page confidence from agreement and a review flag carrying both readings.
- **Tesseract** stays as the fallback if Ollama is unavailable.
- **Hallucination veto in the plan** needs amending: the plan's rule disqualifies any
  engine that invents text in illegible regions, which every vision model does to some
  degree. The proposal is to accept that risk where the second reader flags it and a
  human reviews flagged words. See the results document, "Decision" section.

### Layout choice (open)

| Option | How it works | Measured |
| --- | --- | --- |
| Two Ollama instances | One per GPU, so the 9B is always instantly available on the 3080 Ti and the big model runs elsewhere | Simple; the big model then has less VRAM |
| Pause and swap | One instance; processing is paused (request cancelled by dropping the connection, which works) so the 9B can answer, then the big model reloads | Swap to the 9B about 6.5 s; back to the 27B about 16 s warm, 103 s cold |

Recommendation was to start with two instances and add cancel-and-swap only if needed.
The owner has not chosen.

**Question for next time: two time periods, two modes?** Instead of one layout all the
time, run two modes and switch between them:

- **Interactive mode** (day to day): two models resident (the 9B for quick answers plus a
  second model), so queries respond at once.
- **Ingestion mode** (a deliberate batch run, possibly headless over ssh): every GPU given
  to the big model (`qwen3.6:27b`) for full-on processing, with the 9B as second reader
  afterwards or not loaded at all.

Things to work out: how the switch happens (a script that restarts or reconfigures
Ollama, versus a config flag), whether queries are refused or queued during ingestion
mode, and whether a batch can simply run overnight so no live switching is needed. This
may make the pause-and-swap machinery unnecessary.

## Lessons

- Verify a metric before trusting it: two claims were corrected after remeasuring.
- Ground truth for old documents needs the owner's eyes; the first draft misread names.
- Exact-match second reading beats a classic engine as a checker because the two models'
  errors differ.
- Check GPU health before timing anything.
